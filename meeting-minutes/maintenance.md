# 維護說明

這份給要**修改或維護這個工具**的人：為什麼這樣設計、做過哪些取捨、實測數字是多少。改工具之前先看，才不會把刻意的設計改壞。

只是要安裝、使用的話，看 [README.md](README.md) 就好。

---

## 一場會議是怎麼跑完的

同事在 AI 對話框輸入 `/minutes`，附上錄音、相關檔案、參加者之後，會依序發生：

```
錄音（留在本機）
  │ ① 轉錄：本機的 whisper.cpp 把聲音轉成文字，套用詞彙表修正錯字，並用聲音分出「講者 A／B」
  ▼
逐字稿
  │ ② AI 自己檢查：對照名單、簡報、畫面，改掉確定聽錯的詞，寫進詞彙表
  ▼
會議記錄 ＋ 一張「聽不清楚」的校對表（人可以不填）
  │ ③ 有人填了校對表 → 修正也寫進詞彙表
  ▼
詞彙表變厚 → 下一場轉錄就更準
```

下面各節分別說明這條流程裡每個環節的設計理由。

## ⚠️ 先讀這段：什麼東西會離開你的電腦

| | 會不會離開本機 |
| --- | --- |
| **錄音／螢幕錄影檔** | **不會。** 轉錄完全在本機跑。 |
| **逐字稿文字** | **會。** 寫會議記錄時要交給 AI 工具讀。 |
| **螢幕錄影的截圖** | **會**（只有螢幕錄影才有）。AI 寫記錄時會看這些圖，畫面上的機密跟逐字稿一樣會送出去。 |
| **聲紋**（用來分辨講者的聲音特徵） | **不會。** 只存在本機的 `var/embeddings/`，用途是之後改人數時不必重新轉錄。隨時可以刪。 |

所以**人事、薪資、法務、未公開財務的會議不要用這個工具**，或只做到逐字稿、自己手動整理。這沒辦法靠改設定解決：AI 沒看到文字，就寫不出會議記錄。

另外，詞彙表（`config/glossary.txt`）是全隊共用、會上傳到 GitHub 的，裡面會累積**真實的人名、專案名、客戶名**。所以這個倉庫必須一直維持私有（private）。

## 架構：為什麼分成三層

AI 工具（Claude、Cursor 等）沒辦法直接聽音檔，只能讀文字。所以工作拆成三層：

| 層 | 做什麼 | 在哪 |
| --- | --- | --- |
| 1. 轉錄 | 在本機把錄音轉成逐字稿 | `scripts/transcribe.py` |
| 2. 整理 | 告訴 AI 怎麼把逐字稿寫成會議記錄，以及兩種範本 | `INSTRUCTIONS.md`、`templates/` |
| 3. 入口 | 讓各個 AI 工具多一個 `/minutes` 指令，內容只是「去讀第 2 層的指示」 | `entrypoints/`，安裝後放到 `~/.cursor/commands/minutes.md` 等 |

第 3 層刻意做得很薄：真正的規則都在 `INSTRUCTIONS.md`，而入口是用絕對路徑去讀它。所以改 `INSTRUCTIONS.md` 後，每個人的 `/minutes` 下次就會讀到新內容，不用重裝。只有改了 `entrypoints/` 才需要跑 `./install.sh --update-entrypoints`。

## 檔案放哪，以及為什麼

```
meeting-minutes/               ← 工具本身，用 git 管理，可以整個刪掉重來
├─ config/
│  ├─ glossary.txt             ★ 上 git，全隊共用（校對成果累積在這）
│  ├─ eval-cases.tsv           ★ 上 git，全隊共用（量準確率用的考題）
│  └─ config.yaml                不上 git（每台電腦的路徑不同）
├─ models/                       不上 git（1.6GB，install.sh 會下載）
├─ var/                          不上 git（暫存資料，可以重建）
├─ bin/transcribe                不上 git（裡面寫死了這台電腦的路徑）
└─ scripts/ templates/ entrypoints/ INSTRUCTIONS.md

~/Desktop/會議記錄/            ← 會議資料，刻意放在工具外面
├─ audio/                      ← 待轉的錄音／螢幕錄影
└─ minutes/
   ├─ 2026-07-02-Tw-site-training-1.md     ← 會議記錄（這一場的主檔）
   └─ 2026-07-02-Tw-site-training-1/       ← 同名資料夾：逐字稿、校對表、截圖、舊版
```

**工具的東西全部收在同一個資料夾**，而不是照 Unix 慣例分散到 `~/.config`、`~/.local/share`。因為這個工具要發給同事、詞彙表要共用：全部收在一起，`git clone` 一次就拿到完整一份，移除就是刪資料夾，詞彙表也能直接靠 git 同步。

**會議資料反而放在外面**，因為那是機密內容，不能跟 git 放在同一個資料夾。只要有人一次誤操作（例如 `git add -f`，或改錯 `.gitignore`），整場會議就會被推上 GitHub。

唯一放在這兩個地方以外的，是各 AI 工具的入口檔（`~/.cursor/commands/minutes.md` 等），因為 AI 工具只會去那裡找指令。`./install.sh --uninstall` 會清掉它們。

## 兩種範本：選錯不是格式醜，是內容不見

| 範本 | 用在 |
| --- | --- |
| `templates/minutes.md`（決議型） | 多人開會、有指派、有拍板 |
| `templates/training.md`（教學型） | 一個人講解操作、交接 |

AI 怎麼選，規則寫在 `INSTRUCTIONS.md` 第 4 步。

實測對照：同一份 38 分鐘的教學逐字稿——

- 套**決議型**：產出 3.2 KB。三條「決議」有兩條其實不是決議，待辦只有一條，負責人寫 `@?`。
- 套**教學型**：產出 7.7 KB。操作步驟、指令、容易出錯的地方都在。

受訓的人最需要的操作步驟，套錯範本會被縮成一句「討論了 A 和 B」。對照檔留在會議資料夾的 `minutes/2026-07-02-Tw-site-training-2/2026-09-10-Tw-site-training-2-用minutes範本.md`，要改範本規則前可以先看。

## 詞彙表：為什麼比換更大的模型有效

語音辨識最常錯的是專有名詞和英文術語（例如把「Font Awesome」聽成「鳳猴身」）。換更大的模型幫助有限，把正確的詞直接告訴它效果好得多：實測術語正確率從 **36% 提升到 82%**（單次量測，不是長期追蹤）。

`config/glossary.txt` 在兩個時間點派上用場：

1. **轉錄前當提示。** 把詞彙清單交給 whisper（`--prompt`），讓它知道會出現哪些詞。這裡有 400 字元上限，所以會先排出「最需要提示的詞」再截斷，否則等於由檔案裡的先後順序決定誰被留下。排序邏輯寫在 `transcribe.py` 的 `rank_terms()` 說明，裡面也記了一個已知的干擾因素。
2. **轉錄後直接替換。** `錯詞=>正詞` 這種規則會在轉完後逐字替換，沒有長度限制。能用這種方式修的，就優先用這種。

**全隊共用靠 git，不用另外寫合併程式。** 詞彙表一行一條規則：A 加 3 行、B 加 5 行，`git pull --rebase` 就自動合在一起。AI 校正後會自動跑 `learn.py` 把修正寫進詞彙表，但要讓同事拿到，還要 `git push`。不 push 的代價很實際：五個人各自校對同一個錯字，花五倍人力，只得到一倍效果。

## 校對迴圈：沒有標準答案時怎麼知道有沒有變準

問題是：沒有人會把 38 分鐘的錄音手打一遍，所以沒有標準答案可以對，也就無法知道改了設定之後是變好還是變壞。

做法是讓電腦挑出它自己最沒把握的幾十句，只請人校對那幾句：

```
轉錄 ──► .review.md（只挑幾十句）──► 人填「應該是」──► 丟回對話（自動跑 learn.py）──► eval.py 算分
  ▲                                                                              │
  └────────────── 詞彙表變厚，下次轉錄就對了 ◄───────────────────────────────────┘
```

AI 寫會議記錄時也會另外產出 `.ai-review.md`，記下它從上下文判斷出來的錯字，**同一輪就寫進詞彙表**，不用等人。

### 怎麼挑出可疑的句子

用兩個訊號：

1. **whisper 自己的信心度。** whisper 會標出每個字有多確定（低於 0.33、低於 0.66、0.66 以上三級）。但信心低不代表一定錯，所以這個訊號只拿來**排順序**，最後還是由人判斷。
2. **英文字查字典。** 把英文字拿去比對英文字表（`data/english-words.txt`，跟 macOS 內建的 `/usr/share/dict/words` 同一份）：`section`、`module` 查得到，大概是聽對了；`victify`、`previct`、`mudge` 查不到，幾乎一定是聽錯。whisper 對這種亂拼的字常常很有信心，所以這個訊號能抓到信心度抓不到的錯。

挑選名額會平均分到錄音的 8 個時段，再按「可疑字佔整句的比例」排序。不這樣分的話，名額會被開場幾分鐘（收音差、閒聊）用光，但真正需要校對的術語錯誤多半在中後段的技術內容裡。

已經被詞彙表修好的句子，下次就不會再被挑出來，所以校對清單會越來越短。

### eval.py 的分數要分開看

這種「自己出題自己改」的迴圈有個陷阱：校對過的錯字一定會被詞彙表修好，所以「修正後」的分數必然漂亮，但那不代表辨識真的變準了。所以 `eval.py` 分成幾欄：

| 欄 | 意思 |
| --- | --- |
| 修正後 | 整個流程跑完的結果。有規則的詞應該 100%，低於 100% 代表規則沒生效 |
| **whisper 自己** | 不套詞彙表時 whisper 原本聽對幾成。**只有這個數字上升，才是真的變準** |
| 尚未套用 | 規則比這份逐字稿新，重轉一次就會好，不算失敗 |
| 未涵蓋 | 沒辦法寫成自動判斷的規則，不計分 |

「whisper 自己」用的是 `var/confidence/` 裡、套詞彙表**之前**的原始文字算的，所以不必為了留考題而故意不修錯字。能讓這個數字上升的，是調整略過靜音的門檻、換模型、改轉錄前的提示詞；新增修正規則不會影響它。

有學過的規則沒生效時，`eval.py` 會以錯誤狀態（exit code 1）結束，可以直接接進其他腳本做檢查。

## 防止「幻聽」和漏段

whisper 遇到沒人講話的空檔，有時會自己編出句子（幻聽），或把同一句重複好幾次。對策依效果排：

1. **轉錄前先切掉沒人講話的段落**（用 Silero VAD 判斷哪裡有人聲）。這是最有效的一步，實測幻聽段落從 23 段降到 4 段。
2. **判斷門檻設 0.25**，不用 Silero 預設的 0.5。實測 0.5 會把 **26% 真正在講話的內容**也當成靜音切掉；改成 0.25 後，內容保留率從 88% 回到 94%。理由寫在 `scripts/transcribe.py` 的註解。
3. **whisper 參數** `--suppress-nst`、`--max-context 64`，降低把雜音當成話、或一直複製上一句的機率。
4. **連續重複 3 次以上的句子會被摺疊**，並在逐字稿裡標出時段。
5. **幻聽偏多時會警告**：終端機印出品質警告，檔案照樣寫出，但以 exit code 2 結束。
6. **整理時再檢查一次**：`INSTRUCTIONS.md` 第 3 步要 AI 先看時間軸有沒有大段跳過。跳過的時間加總超過全長 10%，就在會議記錄裡註明「可能漏了約 N 分鐘」，但仍然繼續寫。

## 分辨講者：分得出是不同人，但認不出是誰

逐字稿每次換人講話，會插一行 `**講者 A**`；開頭有一張「誰是誰」的表讓人填名字。做法在 `scripts/diarize.py`，用的聲紋模型是 `3dspeaker_speech_campplus_sv_zh-cn_16k-common.onnx`（28MB）。

**刻意只做「分開」，不做「認人」。** 要讓工具下次自動認出某個人，就得長期保存每個人的聲紋，而聲紋是生物特徵資料。為了會議記錄承擔這種保管責任不值得。代價是每場的代號各自獨立：**這場的講者 A 跟上一場的講者 A 沒有關係。**

### 為什麼不用現成的整套方案（pyannote）

實測遇到兩個問題：

1. **換人的那句最容易標錯。** 它會自己切一套語音段落，再跟 whisper 的句子對時間，兩邊切法對不齊。結果短短的插話（「對啊」「也還好啊」）會被併進前一個人，而這正是讀的人最想知道是誰說的。
2. **人數判斷失準。** 一場 27 分鐘的兩人會議，它自動判斷出 **30～74 個人**（門檻 0.5 到 0.6 之間）。

現在的做法是：直接拿 whisper 已經切好的每一句，各自取聲紋再分組，不跟任何時間軸對位。同一份 27 分鐘錄音只花 **10 秒**（整套方案要 100 秒），結果跟「整套方案＋強制分 2 人」的輸出有 **88%** 一致。

### 人數怎麼決定

不能用固定門檻判斷「兩段聲音像不像同一個人」，因為每份錄音的相似度基準都不一樣。實測三場都是兩人對話，相似度中位數卻分別是 0.369、0.465、0.519；同一個門檻 0.35，在第一場分出 2 人，在第二場只分出 1 人。

改用**輪廓係數**：每份錄音自己跟自己比，看「組內有多像」相對於「跟別組有多不像」。分數最高的人數就是答案。三場都正確判斷為 2 人：

| 錄音 | 長度 | 判斷 | 輪廓係數（分 2／3／4 人） | 兩人講話佔比 |
| --- | --- | --- | --- | --- |
| 設計審查 | 27 分 | 2 人 ✓ | +0.323／+0.318／+0.189 | 75／25 |
| 檢討會 | 14 分 | 2 人 ✓ | +0.200／+0.169／+0.180 | 62／38 |
| 教學（一人講解為主） | 78 分 | 2 人 ✓ | +0.221／+0.085／+0.075 | 69／31 |

### 分錯時很容易改

聲紋會存在 `var/embeddings/<檔名>.npz`，所以改人數不用重新轉錄：

```bash
.venv/bin/python scripts/relabel.py <逐字稿.md> --speakers 3   # 實測 0.13 秒
```

已經填進「誰是誰」的名字不會被蓋掉。`--speakers 1` 用在真的整場只有一個人講的教學。

沒裝聲紋套件（sherpa-onnx）或沒下載聲紋模型時，這個功能會直接略過，逐字稿照樣產出。分講者只會插入講者標題行，`[HH:MM:SS] 內容` 那些行**一個字都不會動**，因為 `review.py`、`eval.py` 靠這個格式讀逐字稿。

## Windows 版：同一份工具包，只有安裝不同

Mac 和 Windows 共用同一個資料夾、同一份 `INSTRUCTIONS.md`、範本、詞彙表。Python 腳本本來就跨平台，
差別只在「元件怎麼裝」和幾個 Windows 才有的坑。安裝走 `install.cmd` → `install.ps1`（`install.sh` 的對應版）。

| 項目 | Mac | Windows | 為什麼 |
| --- | --- | --- | --- |
| 裝元件 | Homebrew | winget（`Gyan.FFmpeg`、`astral-sh.uv`、`Git.Git`） | winget 是 Win10/11 內建的 |
| whisper | `brew install whisper-cpp` | 官方編好的 `whisper-bin-x64.zip` v1.9.2，放 `tools\`，核對 sha256 | 跟 Mac 同一版；CPU 版任何電腦都能跑 |
| 模型 | Apple Silicon 用 turbo，Intel 用 medium | turbo | 沒有 GPU 時 turbo 跟 medium 差不多慢但中文較準；跟 Mac 同一個模型，共用詞彙表效果才一致 |
| 執行緒 | whisper 預設 | `-t min(8, CPU 數)` | whisper 預設最多 4 條，一般筆電可以多給 |
| 英文字表 | `/usr/share/dict/words` | repo 內的 `data/english-words.txt` | Windows 沒有這個檔；內容是同一份（Webster's 2nd，公版） |
| 入口檔 | 偵測得到才裝 | 四個全裝 | 同事用的 AI 工具比較雜，偵測不可靠；多裝只是多一個小檔 |

**Windows 才有的坑，以及怎麼處理的：**

- **whisper 收到的參數是系統編碼（台灣是 Big5），中文提示詞會變亂碼。** 這是 whisper.cpp 原始碼自己註明的限制。
  解法：`transcribe.py` 把參數寫進一個 UTF-8 檔，只傳 `@檔名` 給 whisper，它會一行一行原樣讀進來（`windows_response_file()`）。
- **上面那招只救得了文字，救不了路徑。** 模型、音檔的路徑有中文時 whisper 一樣開不了檔。所以：
  暫存資料夾放在 repo 的 `var/tmp/`（使用者名稱可能是中文，系統暫存資料夾就不安全），
  而且 **repo 本身必須放在沒有中文的路徑**（建議 `C:\meeting-minutes`）。`install.ps1` 一開始就檢查，不合格直接停。
  會議資料夾（桌面的「會議記錄」）可以有中文：只有 ffmpeg 會讀它，ffmpeg 讀得到。
- **主控台預設 Big5，印 ✓、⚠️、⟦⟧ 會當掉。** `paths.py` 在 Windows 上把 stdout／stderr 改成 UTF-8，每支腳本都會 import 它。
  呼叫外部程式抓輸出的地方也都指定 `encoding='utf-8'`（ffmpeg 會印出中文檔名）。
- **YAML 雙引號裡的 `\U` 是跳脫字元**，`"C:\Users\…"` 會讀壞。`install.ps1` 寫 config 時路徑一律轉成正斜線。
- **PowerShell 5.1 讀沒有 BOM 的 UTF-8 腳本會把中文當 Big5。** `install.ps1` 必須存成 UTF-8 含 BOM；
  `install.cmd` 則只能有英文（cmd.exe 在切換編碼之前就先讀檔了）。行尾由 `.gitattributes` 固定成 CRLF。
- **Windows 預設不讓人執行 .ps1。** `install.cmd` 用 `-ExecutionPolicy Bypass` 叫它，同事不必改系統設定。
- **winget 裝完的程式，已經開著的 AI 工具看不到**（PATH 要重開才更新）。`install.ps1` 把 ffmpeg、ffprobe、
  whisper-cli、python 的絕對路徑寫進 config（`ffmpeg`、`ffprobe`、`whisper_cli`、`python_path`），`transcribe.py` 先讀 config 再找 PATH。
- `INSTRUCTIONS.md` 的指令一律用 config 的 `python_path`，不寫死 `.venv/bin/python`（Windows 是 `.venv\Scripts\python.exe`）。

## 已知問題

- **漏段警告會誤報螢幕分享型錄音。** 上面「超過 10% 就註明」的規則，在 2026-09-11 那場跳過了 15.1%，但抽查後發現是講者在等 AI 跑結果的空檔，加上室內音響的底噪，**並沒有漏掉內容**。應該改成先自動抽查，再決定要不要警告。
- **Intel 的轉錄速度還沒實測過**，使用流程裡的時間是估計值。
- **Windows 版完全沒在真的 Windows 上跑過。** 邏輯是照 whisper.cpp 原始碼和 Windows 的行為寫的，第一個裝的同事很可能會遇到問題，請他們把錯誤訊息整段傳回來。最可能出事的地方：winget 在公司電腦被停用、`whisper-cli.exe` 缺 VC++ 執行元件（`install.ps1` 會試著補裝）、轉錄速度比估計慢。
- **Windows 版的速度是估計值**，`INSTRUCTIONS.md` 第 0 步的「5 分鐘以內在對話裡轉」要等實測後再調。
- **術語正確率 36% → 82% 只量過一次**，還不是長期追蹤的數字。

## 這個工具不做的事

- 不管理任務狀態、不改專案進度資料庫
- 不同步 Figma
- 不做開會當下的即時轉錄
- 不把錄音檔上傳到任何雲端服務
- 不建立聲紋檔來認人（只分不認，見上）

Notion 整合是選配：只有 AI 工具裡接了 Notion 時才會做，而且只會寫入「會議記錄」資料庫。

## 附錄：`transcribe.py` 可調參數

| 參數 | 作用 |
| --- | --- |
| `--model` | 指定 whisper 模型 |
| `--glossary` | 指定詞彙表路徑 |
| `--output-name`、`--output-dir` | 指定輸出檔名與資料夾 |
| `--no-vad` | 不先切掉靜音段落 |
| `--vad-threshold`、`--vad-speech-pad-ms` | 調整靜音判斷的門檻，以及人聲前後保留多少毫秒 |
| `--no-review` | 不產生校對表 `.review.md` |
| `--review-max-rows` | 校對表最多挑幾句 |
| `--no-frames` | 螢幕錄影不抽截圖 |
| `--no-speakers` | 不分講者 |
| `--speakers N` | 直接指定有 N 位講者 |

輸入是螢幕錄影時，會在講者說「你看這個」之類的地方附近抽截圖，最多 16 張，清單在 `<逐字稿>.frames.md`。純錄音檔會跳過這步。
