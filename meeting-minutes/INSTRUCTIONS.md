# 會議記錄產出指示（Layer 2）

> 這份檔案是唯一指示來源。Cursor / VS Code / Codex / Claude Code 的入口檔案都只是薄包裝，
> 讀完這份就照著做。若所有 slash command 都掛了，使用者也可以直接把這份貼給 AI（保底方案）。

給 AI 讀的：以下是你要執行的流程。**先讀完再動手。**

**預設行為：使用者丟語音檔或螢幕錄影進來，同一輪就要做完。**
使用者通常會在同一則訊息給三樣東西：音檔或 mp4、相關檔案（PPT、PDF、Excel 等）、參加者是誰與有幾位。
轉錄（含術語表錯詞修正）→ 存逐字稿 → 有影像軌就抽關鍵畫面 → **自己 review 一次逐字稿** → 立刻寫會議記錄並存檔。
同一輪要交出會議記錄，以及聽不清楚、給人看的 `.review.md`。那張人工表**不必填**；你確定的錯詞不要等它，寫完 `.ai-review.md` 就跑 `learn.py`。
**不要**轉完逐字稿就停下來等使用者說「繼續」；**不要**為了問參加者／類型而中斷產出。
人名單與人數以使用者這一輪寫的為準。缺的資訊用逐字稿推斷，推不出就標 `@?`。
逐字稿已經用聲紋標好「講者 A／B」代號了，你的工作是把代號對上真名（見第 5 步）。

**對話裡不要貼會議記錄全文，也不要貼逐字稿全文。** 只回報：檔案位置、需要人補的地方、品質／詞表等重要資訊。全文去開檔。

---

## 0. 先決定要不要在這裡轉錄（最容易踩的坑）

| 情境 | 做法 |
| --- | --- |
| 使用者給的是逐字稿 `.md` | 跳過轉錄，直接進第 4 步 |
| 短錄音（預估轉錄 ≲ 10 分鐘，多半是 Apple Silicon） | 可以在這裡呼叫 `transcribe.py` |
| 長錄音，或 `arch: intel`／`arch: windows` 且預估 ≫ 10 分鐘 | **不要在這裡跑。** 印出建議的終端機指令（見第 2 步的「給使用者自己跑」）與預估時間，結束本輪，等使用者帶逐字稿回來 |

預估方式：Apple Silicon + `large-v3-turbo` **實測 1 分鐘音訊 ≈ 3 秒**
（2026-09-11 實測：37.9 分鐘 → 1 分 56 秒）；Intel + `medium` 約 **1 分鐘音訊 ≈ 60–90 秒**
（估計值，未實測）；Windows（`arch: windows`，只有 CPU）+ `large-v3-turbo` 約 **1 分鐘音訊 ≈ 1–3 分鐘**
（估計值，未實測，看電腦）——大約 **5 分鐘以內的錄音**才在這裡轉。
用 `ffprobe` 取得時長後估算（Mac 也可以用 `mdls`），不要憑感覺。`ffprobe` 的路徑：config 有 `ffprobe` 鍵就用它，否則直接打 `ffprobe`。
超過 10 分鐘就走上表第三列 —— 照實測速度，Apple Silicon 要到**約 3 小時的錄音**才會超過。

## 1. 讀設定檔

讀 `<repo_dir>/config/config.yaml`（schema 見 SPEC §5.3）。`repo_dir` 就是本檔案
所在的資料夾——入口檔裡已經寫好了絕對路徑，直接用，**不要去猜家目錄下的位置**
（舊版曾放在 `~/.config/meeting-minutes/`，現在一律收在 repo 內）。需要用到的鍵：

`repo_dir`、`template_path`、`audio_dir`、`minutes_dir`、`glossary_path`、`model`、`models_dir`、`arch`、`python_path`、`notion.database_id`

**本檔所有指令裡的 `"$python"`** ＝ config 的 `python_path`。舊設定沒有這個鍵時：Mac 是 `$repo_dir/.venv/bin/python`，Windows 是 `$repo_dir/.venv/Scripts/python.exe`。

**Windows（`arch: windows`）**：終端機通常是 PowerShell。指令照抄，但開頭加 `& `（PowerShell 要這樣才會執行引號裡的程式），例如
`& "C:/meeting-minutes/.venv/Scripts/python.exe" "C:/meeting-minutes/scripts/transcribe.py" "<音訊路徑>"`。
路徑用正斜線 `/` 也可以。不要用 `mdls`、`open` 這類 Mac 才有的指令。

`transcripts_dir` 是舊鍵，只當尋檔後援。新產出一律寫進 `minutes_dir`：會議記錄在根目錄，逐字稿／校對／畫面在同名資料夾。

**不存在 → 停下來，請使用者先安裝（Mac 跑 `install.sh`，Windows 跑 `install.cmd`）。** 不要自己猜家目錄路徑硬編進指令。

## 2. 解析輸入

| 使用者給的 | 行為 |
| --- | --- |
| 音訊／視訊路徑 | 依第 0 步決定在這裡轉或請使用者去終端機轉。`.mp4`／`.mov` 等螢幕錄影同一條指令；`transcribe.py` 會抽關鍵畫面 |
| 同一則訊息裡的 PPT、PDF、Excel、CSV 或其他參考檔 | **不要轉錄。** 寫會議記錄前先讀。數字、名單、頁碼以檔案為準，讀不到就在對話裡說明，不要猜 |
| 已存在的逐字稿 `.md` | **跳過轉錄**，直接進入第 4 步。相關檔案與參加者名單仍要讀 |
| 相對路徑 | 先相對**當前工作目錄**；找不到再依序試 `audio_dir`、`minutes_dir`（含子資料夾）、`transcripts_dir`；仍沒有 → 問使用者完整路徑 |
| 僅檔名 | 在 `audio_dir`／`minutes_dir`（含子資料夾）搜尋；多筆相符 → 列出請使用者選 |
| 什麼都沒給 | 問要處理哪個檔案。不要自己去 `audio_dir` 挑最新的那個 |

轉錄指令（路徑一律從 config 組，檔名有空白要引號）。**不要**再指定 `--output-dir`，
`transcribe.py` 會寫進 `<minutes_dir>/<錄音日>-<slug>/`：

```bash
"$python" "$repo_dir/scripts/transcribe.py" "<音訊路徑>"
```

**給使用者自己跑**（第 0 步判定不在這裡轉時，印這一行給他們，路徑換成實際的）：

- Mac（終端機）：`"<repo_dir>/bin/transcribe" "<音訊路徑>"`
- Windows（PowerShell）：`& "<repo_dir>/bin/transcribe.cmd" "<音訊路徑>"`

並告訴使用者：轉完畫面最後會印「完成：<逐字稿路徑>」，把那個路徑貼回對話、再輸入 `/minutes` 就好。

轉完後確認逐字稿檔案存在且非空，**立刻進第 3 步勘查並寫會議記錄**。
不要把「逐字稿好了」當成結束。轉錄失敗就把 stderr 原文貼給使用者，不要自己重試三次。

## 3. 讀逐字稿，先做一次品質勘查

讀完整份，**不要只讀前 200 行就開始寫**。同時看三件事：

1. **時間軸有沒有大跳號。** 相鄰兩行時間差 ≳ 25 秒就是可疑段落（VAD 可能切掉了語音）。
   若整份累計跳號超過總時長 10%，在會議記錄裡註明「這份逐字稿可能漏了約 N 分鐘（或只是螢幕分享靜默）」，
   **仍繼續整理**，不要停下來問要不要重跑。使用者看完再決定要不要降 `--vad-threshold` 重轉。
2. **有沒有重複幻聽殘留。** 同一句連續出現 3 次以上，當作雜訊忽略，不要寫進記錄。
   `transcribe.py` 已摺疊過的段落會留 `> ⚠️ 已摺疊重複幻聽` 標記，直接跳過。
3. **有沒有大量音譯亂碼**（英文術語被聽成中文亂字）。整理過程中只要從上下文推斷出
   某個詞其實是什麼，就記下來（時間戳、聽成什麼、應該是什麼），第 7 步要用。
   你抓到的錯誤跟工具自己抓的**不重疊**：`.review.md` 是靠 whisper 的信心度挑行，
   而音譯亂碼 whisper 往往很有信心，只有讀得懂上下文的你看得出來。
4. **有沒有畫面截圖。** 逐字稿旁邊若有 `<stem>.frames.md`，**寫會議記錄前先讀索引，
   再用 Read 把裡面列出的 JPEG 都看過**（最多約 16 張）。講者說「你看這個」時，
   路徑／檔名／按鈕以畫面為準寫進筆記。圖空白、載入中、字太小讀不到，才標 ⚠️。
   沒有 `.frames.md` 就當純錄音，不要自己去源檔抽圖。
5. **幾個人在講，代號對得上誰。** 逐字稿開頭有「講者：N 人」與「誰是誰」表格，
   內文每次換人會插一行 `**講者 A**`。這是聲紋自動分的，**它只知道「這兩段是不同人」，
   永遠不知道名字**——名字要你從對話內容推（見第 5 步）。
   讀的時候順手核對人數：對話裡明明有三個人互相喊名字、表格卻只寫 2 人（或反過來，
   整場其實只有一個人在講、卻分出 3 人），就是分錯了。分錯的處理方式：
   ```bash
   "$python" "$repo_dir/scripts/relabel.py" "<逐字稿.md>" --speakers N
   ```
   幾秒鐘就好，**不用重新轉錄**，跑完重讀逐字稿再繼續。改不動（說沒有聲紋快取）
   就照現有代號寫下去，並在會議記錄開頭註明「講者代號可能不準」。
   沒有「誰是誰」表格＝這份是舊逐字稿或聲紋模型沒裝，照第 5 步自己從對話分。
6. **有沒有投影片／文件／表格。** 使用者這輪有附 PPT、PDF、Excel、CSV、講義、Figma，寫之前先讀。
   對得上的段落要標來源（見第 6 步）。Excel／CSV 用來核對數字、名單、表頭，不要把整表貼進會議記錄。
   `.pptx` 或試算表讀不到就改看畫面截圖上的頁碼／標題，以及講者念出的頁數，並在對話裡說明哪一份沒讀到。
   看不到頁碼就標投影片標題，**不要猜第幾頁**，也不要猜表格裡的數字。

## 4. 選範本

`template_path` 指的是預設範本（`templates/minutes.md`）。同目錄下還有其他範本，依錄音性質選：

| 範本 | 什麼時候用 | 判斷訊號 |
| --- | --- | --- |
| `minutes.md` | 決議型會議 | 多人輪流發言、出現「我們決定」「那就這樣」、有人被指派工作 |
| `training.md` | 教學／交接 | 一人長時間獨白、螢幕分享、「你只要看這三份」「你不要去做…」、幾乎沒有決議 |

**判斷錯了比格式醜更糟。** 教學型錄音套 `minutes.md` 會產出空的決議與空的
待辦，看起來像沒開過會；決議型會議套 `training.md` 會把爭論寫成步驟。

不確定就選你比較有把握的那一種，在會議記錄開頭用一行註明判斷理由
（例如「整份 90% 是同一人在講操作步驟，用教學型」）。使用者看完再說「改用 minutes 範本」再重寫。

## 5. 中繼欄位：自己填，不要停下來問

讀完逐字稿、選好範本之後，**立刻往第 6 步寫**。下面這幾項用逐字稿與檔名推斷：

1. **參加者**：人名與人數以使用者提供的為主，不要用推斷蓋掉。

   使用者寫了「有幾位」（例如 3 位），而逐字稿開頭的「講者：N 人」不是這個數字，
   **先**跑 `relabel.py --speakers N`、重讀逐字稿，再往下寫。不要帶著錯誤人數寫完才講。

   **開頭資訊表只列這場有出席的人。** 錄音裡被提到、但沒有來開會的
   （拿來當例子的 Alan、拿來對照的 Sharon）不要寫進「參加者」。
   那些人若跟結論有關，寫在討論細節即可。

   **寫法（同一格、每個人一行，用 `<br>` 換行）：**

   - 主持這場會的人（開場、排程、指派、拍板）在名字後面標 `（主持人）`
   - 其他與會者**只寫名字**。不要標「非主持人」，也不要標「講者 A／B」或「講解／提問」
   - 不要寫成 `Joyie（講者 A，講解）`——逐字稿代號留在逐字稿「誰是誰」表格，不進會議記錄開頭
   - 分不出誰在主持，就全部只寫名字，不要猜、也不要人人都標主持人
   - 推不出名字、但分得出是不同人：主持的那位寫 `主持人`，其他人寫 `與會者`（仍一人一行）。連幾個人都分不出來才寫 `@?`

   範例：

   ```
   | 參加者 | Joyie（主持人）<br>Zoe |
   ```

   **優先序（從高到低）：**

   | 優先 | 來源 | 寫法 |
   | --- | --- | --- |
   | 1 | 這一輪使用者明確給的名單 | 整份用這些名字當主標。待辦寫 `**Joyie**：`，不要寫 `**講者 A**：`。參加者列：主持人標 `（主持人）`，其他人只寫名字 |
   | 2 | 逐字稿裡被喊到、對得上術語表的名字 | 同上；確認這個人有出席，不是只被提到 |
   | 3 | 分得出是不同人，但沒有提供、也沒喊到名字 | 參加者列用 `主持人`／`與會者`，內文才用逐字稿代號 |
   | 4 | 連幾個人都分不出來 | 才寫 `@?` |

   使用者給過名單，就用那份，不要再用逐字稿自己猜一組蓋掉。
   逐字稿已經把人分成「講者 A／B／C」了，**你要做的是把代號對上上面那些名字**，
   用在待辦、決議、討論細節；**不要把代號抄進參加者列**。
   聲紋只能分出「這是不同的兩個人」，名字只能從「使用者提供」或對話內容看出來。沒有提供名單時才這樣推：

   | 線索 | 例子 |
   | --- | --- |
   | 有人被叫名字，下一句換人回答 | 「Joyie 你那邊呢」→ 接著講的那個代號就是 Joyie |
   | 有人自稱 | 「我是負責前端的」＋術語表對得上 |
   | 誰在主持 | 開場、排議程、指派待辦、拍板的那位 → 參加者列標 `（主持人）` |

   **不要整場都寫 `@?`**——那會讓不同的人長得一模一樣，讀的人分不出誰是誰。
   真的連幾個人都分不出來（收音差、單人錄音、沒有「誰是誰」表格）才寫 `@?`。

   名字有推出來的話，**順手把逐字稿「誰是誰」表格的 `@?` 也填掉**（只填你有對話證據的，
   沒證據的留 `@?`）。那張表填過就會留著，之後重標人數不會被蓋掉。

   代號一旦指定，**內文前後一致**，同一個人不要前面 `Zoe` 後面 `講者 B`。
   使用者之後說「講者 B 是 Zoe」就整份替換。
   `@?` 留給「這件事不知道該誰做」——那是要人補的洞，跟「知道是哪一位、只是沒名字」不一樣。
2. **會議類型**：給你的判斷（設計審查／同步會議／啟動會／腦力激盪／教學・交接）。
3. **相關檔案**：這次使用者有提供給你的素材才寫，放文末「相關檔案」區塊，
   每筆 `- 名稱：完整路徑或連結`。包括錄音／螢幕錄影、投影片、PDF、Excel、Figma。
   錄音路徑用使用者給的那個，或抄逐字稿開頭的「路徑」列。
   會議裡提到但沒給檔案或連結的，不要列。沒有任何一筆就整段刪掉，不要留空標題，也不要寫「無」。
   逐字稿已經在開頭資訊表，這裡不必再列。
4. **主題、逐字稿**：主題從檔名或逐字稿推；逐字稿放開頭資訊表、緊接在「主題」下面。沒有逐字稿就刪那一列。

同一輪對話裡使用者**已經給過**參加者／類型／連結，就用他給的，不要蓋掉。
有提供人名時，參加者、待辦、決議、討論細節一律用那些名字當主標。
推斷結果寫在會議記錄裡，對話的「其他」只帶一句（例如「參加者寫成 Joyie、Zoe」）。

## 6. 產出

依選定範本寫一份會議記錄。範本檔開頭的 HTML 註解是寫給你看的規則，**產出時要刪掉**。

### 寫法規則（最常出問題的地方）

會議記錄要讓人**打開第一個畫面就知道結論是什麼、自己要做什麼**。寫成逐段轉述的流水帳
就算內容全對也是失敗品。以下規則優先於「把聽到的都寫進去」：

| 規則 | 說明 |
| --- | --- |
| 區塊順序照範本，不要照時間 | 決議型：總結 → 待辦 → 決議 → 還沒決定 → 討論細節（→ 風險 → 相關檔案）。教學型：總結 → 怎麼做 → 注意事項 → 教學細節（→ 後續 → 待確認 → 相關檔案）。**不要**按發言順序或投影片頁碼當主結構，那是講者的順序，不是讀者要查東西的順序 |
| 沒參加過這場會的人要讀得懂 | 每句有主語：寫「這套工具／會議記錄／逐字稿」，不要用「她」「它」。現場口語（「還不如」「好超扯」「看真的不知道」）改寫成完整意思。省略主語、截一句對話當記錄＝失敗 |
| 不要複述對話、也不要「A 說 B 說」 | 「Joyie 說…後來 Zoe 說…」一律禁止。會議記錄的意義是總結，不是逐字稿縮寫。寫成「結論 ＋ 原因」。來回對話、誰講了哪句原話都不要留 |
| 討論細節先列結論，再寫提問重點 | 這一節不是把發言再列一次。每個 `###` 主題下面直接列已確認的結論（不要寫「項目結論」四個字）；提問重點寫「誰提出了哪個關鍵問題或決策」，之後要討論才知道找誰。格式見下方 |
| 人名放在提問重點，不掛在結論後面 | 已確認的事實不要寫「（Joyie 提出）」，也不要把人名當主詞。錯：`- Joyie：…`、`- Joyie 問：…`、`- Joyie 認為…`。提問重點不要標「問題／決策」。0 人、1 人、多人都合法 |
| **閒聊全部刪掉** | 開場寒暄、等人到齊、「聽得到嗎」「我分享一下畫面」、設備與連線問題、午餐與行程、離題玩笑、與主題無關的個人經驗、單純抱怨、結尾道別 —— 一律不寫，連「（略）」都不要留。判準：這句話拿掉之後，會不會少掉一個結論、原因、待辦、風險或數字？不會就刪 |
| 看起來像閒聊但要留的 | 設備問題造成的結論（「所以這次不錄了」）、客戶反應與客訴內容、講者抱怨裡夾帶的限制（「那個 API 動不了」）、順口提到的期限或人名。留的時候寫成結論句放對區塊，不要保留閒聊的口氣 |
| 現場問答只留「問題 ＋ 回答結論」 | 不要記誰在第幾分鐘問、也不要保留來回對話。答案被收在「概念知道就好」這種軟結論時，就照實寫成一句軟結論，不要自己補成明確答案 |
| 每個主題的結論要能單獨成立 | 每條 `- **標籤**：完整句` 沒參加的人只看這句就懂。沒有結論就寫「沒有結論，見『還沒決定』」。沒有可歸到人的關鍵問題／決策就整段省略「提問重點」，不要硬加人 |
| 散文不超過 3 行 | 超過就拆 bullet。一條 bullet 一行。**總結除外**：總結用合成段，不要拆成標籤清單 |
| 同一件事只寫一次 | 已寫進待辦／決議／注意事項的，細節區不要重講，只補「為什麼」 |
| 待辦要能單獨看懂 | 誰 ＋ 動什麼（哪個畫面／檔案／設定，改成什麼）＋ 做完長什麼樣或交給誰。「做小改」「優化一下」「研究看看」等於沒寫；寫不出具體內容表示會議沒講清楚，改放「還沒決定」。不是行動的事（環境現況、觀察）不要塞進待辦 |
| 「還沒決定」要帶選項與卡點 | 問題 ＋ 有哪些選項 ＋ 卡住誰或什麼 ＋ 該誰拍板。只丟問句等於沒寫；逐字稿沒講選項就寫「會議沒講到」 |
| 教學型條列重點、寫結論，不要抄投影片 | 第 2、4 節寫「之後怎麼做／為什麼」。投影片頁碼標在標題後面當來源即可。講者只是把投影片念一遍、沒有額外結論的條目（例如「第一輪／第二輪」「每輪怎麼計價」）不要再列一次——看投影片或逐字稿就好 |
| 「總結」寫確認後的結果，不要截片段貼標籤 | 1–3 句合成：這場是什麼會、實測／討論確認了什麼、接下來怎麼優化或誰要動。**禁止** `**在處理什麼**`／`**結果**`／`**接下來**`／`**教了什麼**` 這種拼盤。兩種範本標題都寫 `## 1. 總結` |

**討論細節每個 `###` 長這樣（決議型）：**

```
### 主題名稱

- **短標籤**：沒參加這場會的人只看這句就懂的完整答案。
- **另一標籤**：另一條已確認的限制、結果或原因。

**提問重點**：

Joyie
- 用影片／畫面讓 AI 自動判斷發言者是否可行
- 重點正確率低於約 50% 作為停損門檻

Zoe
- 重疊語音與聽不清處要能標時間軸，方便人工回聽
```

- **結論**：這題已經確認的能力／限制／結果／原因。主題標題下面**直接列**，不要寫「項目結論」或「結論」當小標。每條 `- **短標籤**：完整句`，最多約 3–6 條。人名不要出現在這一塊（不當主詞、不掛「提出」）。
- **提問重點**：之後要再討論這件事，打開就能知道該找誰。寫「誰提出了哪個關鍵問題或關鍵決策」，**不是**「誰問了哪句話」。
  - 直接列重點，**不要**標「問題」或「決策」
  - 寫成之後找得到人的重點，不要用「是否能…？」「會不會…？」去複述現場問句
- **人數：0、1、多人都合法。** 不要為了填格式硬加一個人。
  - **多人**：每人單獨一行當分組，下面列那個人提出的重點（上面範例就是兩人）。
  - **一人**：只寫那一組。
  - **沒有人**（分不出是誰、現場沒點名）：`**提問重點**：` 下面直接列 bullet，不要寫「與會者」「某人」。
  - **沒有可歸到人的關鍵問題／決策**：整段省略「提問重點」，連標題都不要留。
- 人名當分組時**單獨一行**（不要 `- Joyie：`）。同一個人的放同一組；分不出是誰就只寫重點、不要猜。
- 同一件事：上面列確認後的結果（不掛名）；提問重點只標「是誰提出的」。不要把完整結論再講一遍，也不要跟「還沒決定」的選項／卡點重複。
- 沒有可寫的結論 → 第一條寫「沒有結論，見『還沒決定』」，不要留空標題。
- 只有「沒有結論，見『還沒決定』」這種單句可以不標籤。不要寫 `**項目結論**：`／`**結論**：`，也不要再寫「（誰提出）」。

### 品質規則（比格式重要）

| 規則 | 說明 |
| --- | --- |
| 只寫逐字稿或畫面上有的內容 | 寧可少寫也不編造。會議記錄的價值在可信。畫面截圖能讀到的路徑／檔名可以寫 |
| 標注來源 | 內容對得上投影片、文件、Figma、畫面時，在該段 `###` 標題後面標。同一段換頁／換檔，才在那一條再標。格式：`（投影片第 12 頁）`、`（投影片〈標題〉）`、`（Figma「Homepage」）`、`（畫面 00:12:03）`。頁碼必須來自檔案、畫面或講者口述；對不上就用標題，不要猜。沒有對得上的來源就不要硬標 |
| 語意不清要標記 | 用 `> ⚠️ 此處逐字稿不清楚（去聽錄音 HH:MM:SS）：<原文片段>`，不要自己選一個解釋。時間戳抄逐字稿那一行的 `[00:06:07]`。同一條有多句就寫 `00:09:26、00:09:43`。逐字稿有章節／題節就加「請看逐字稿〈某段〉」。因為搶話、多人同時講而糊掉，加一句「因為搶話，需重聽錄音」。沒對上時間就不要標 ⚠️ |
| 決議與討論分開 | 「大家覺得可以考慮」不是決議，放討論或未決問題 |
| 負責人不推測 | 有提供人名就用那個名字當主標。沒有名字才用「主持人／與會者」。連是哪一位都分不出來才寫 `@?`。參加者列不要寫講者代號 |
| 期限不推測 | 會議中沒講日期就不寫 |
| 一律繁體中文 | 技術術語（Figma / build / commit）保留原文 |
| 選填區塊沒素材就整段刪 | 不要留空標題充版面 |
| 指令與路徑照抄 | 一字不改，用 `code` 包起來。聽不清楚一定要標 ⚠️，猜錯會害人打錯指令 |

難以辨識時這樣寫（時間必填；有章節、搶話就補上）：

```
> ⚠️ 此處逐字稿不清楚（去聽錄音 00:05:03）：`同時有兩三個人說話`。請看逐字稿〈某某段〉。因為搶話，需重聽錄音。
```

講者說「你看這個」「這裡有寫」但沒念出內容時：
- **有對應截圖且讀得清** → 把畫面上的路徑、檔名、按鈕、指令寫進筆記（用 `code` 包）。
- **沒有截圖，或圖讀不到** → 標 `> ⚠️ 此處講者指向畫面，錄音未帶到內容（去聽錄音 HH:MM:SS）`，不要從上下文推測畫面上是什麼。

### 長逐字稿策略

觸發條件：逐字稿 **超過 600 行或約 15000 字**（先用這個閾值，實測後再調）。

1. 以時間軸切段（每 10–15 分鐘一段，優先切在話題轉換處），各段先產出該段的
   決議／討論／待辦／未決問題草稿（教學型：依實際教學主題整理內容與注意事項，不要硬套檔案結構／步驟／指令／慣例）
2. 再做一次合併整理：去重、統一用語、產出完整待辦，最後才寫「總結」
3. **合併時要重排，不是把各段草稿接起來。** 同一件事散在三段就併成一條；
   照範本的區塊順序落位（結論與待辦在前、細節在後），不要留下按時間排的痕跡
4. 合併時仍遵守上面的寫法與品質規則。**合併是刪重複、重排，不是補內容** ——
   段落草稿裡沒有的東西，不要在合併時冒出來

### 存檔前自檢（寫完先自己過一遍，不要存了才發現）

寫好但**還沒寫入檔案**前，逐條檢查。任何一條答「不是」就**先改再存**，
不要存進去等使用者發現。檢查完不必回報清單本身，改了什麼寫進對話的「其他」一行就好。

## 7. 一律執行這幾件事

同一輪必須把**逐字稿**和**會議記錄**都寫進磁碟，缺一不可。

1. **逐字稿**：`transcribe.py` 已寫入 `<minutes_dir>/<YYYY-MM-DD>-<slug>/`（含詞表 `錯詞=>正詞` 校正）。校對清單、畫面截圖也放這個同名資料夾。
2. **寫入會議記錄**：`<minutes_dir>/<YYYY-MM-DD>-<slug>.md`
   - 日期用錄音日期（取自檔名或檔案 mtime），不是今天
   - slug 用逐字稿／錄音檔名，空白轉 `-`；檔名尾端若已有錄音日（`20260702`）要拿掉，不要重複
   - 同名資料夾與會議記錄檔 stem 必須一致，例如 `2026-07-02-Tw-site-training-1.md` 配 `2026-07-02-Tw-site-training-1/`
   - 同名會議記錄已存在 → 新的一版寫進同名資料夾（例如 `-重轉.md`），不要默默覆蓋根目錄那份，也不要停下來問
   - 對照組、舊版、測試逐字稿都放同名資料夾，不要再堆在 `minutes/` 根目錄
3. **存檔後立刻跑格式檢查，`❌` 要修到沒有才算完成：**

   ```
   "$python" "$repo_dir/scripts/lint_minutes.py" "<剛寫好的會議記錄>"
   ```

   它只檢查結構（區塊順序、結論行、待辦格式、殘留註解），不評價內容。
   - `❌ 錯誤` → 回去改檔案，再跑一次，直到沒有 ❌
   - `⚠️ 提醒` → 靠關鍵詞猜的，自己判斷。真的該改就改；判斷是誤判就留著，**不要為了讓它閉嘴去改掉本來正確的內容**
   - 不要為了通過檢查而刪掉有素材的內容，或編造內容去填必填區塊
4. **對話只回報重點，禁止貼全文。** 會議記錄與逐字稿都不要印在對話裡。固定用這個結構：

   ```
   完成。

   檔案
   - 會議記錄：<路徑>
   - 逐字稿：<路徑>
   - 校對清單：<路徑>（若有）
   - 畫面截圖：<路徑>（若有 .frames.md）

   需要你協助
   - （⚠️、@?、沒聽清的指令／路徑、畫面沒帶到的內容；沒有就寫「沒有必須現在補的」）
   - 人工校對表：<路徑>（選填，不填不影響這份會議記錄；填完再丟回對話才會進詞彙表）

   其他
   - 範本：教學型／決議型（一句理由）
   - 講者：分出幾人、你把哪個代號對成誰、憑什麼（例如「B 有人喊他 Joyie」）
   - 品質：時長、跳號／漏段、詞表這次新增幾條
   - 格式檢查：通過／修了哪幾項；留著沒改的 ⚠️ 提醒是哪一條、為什麼判斷是誤判
   ```

   參加者若是推斷的，放在「其他」一行帶過（例如「參加者寫成 Joyie、Zoe」），不要為此中斷。
   代號對不上名字（表格還留 `@?`）也只是一行帶過，並告訴使用者：
   「逐字稿開頭那張表填一次名字就好，之後重標不會被蓋掉。」
   人數看起來不對就直接說一句「覺得不對的話跑 `relabel.py <逐字稿> --speakers N`，幾秒鐘」。
5. **回饋辨識錯誤**（第 3 步記下來的那些）。整理完之後，把它們寫成
   `<逐字稿同目錄>/<逐字稿 stem>.ai-review.md`，格式必須跟 `review.py` 產生的
   校對表一致，`learn.py` 才讀得懂：

   ```markdown
   | 時間 | whisper 聽到的（⟦⟧ 是可疑處） | 應該是 | 為什麼被挑出 |
   | --- | --- | --- | --- |
   | `00:23:50` | 我用的是Fone OS | 我用的是 Font Awesome | AI 從上下文判斷 |
   ```

   - 「應該是」要填**整句**，不是只填那個詞（`learn.py` 靠整句比對推規則）
   - **沒有把握就不要寫。** 猜錯會把錯規則寫進詞表，污染以後每一份逐字稿；
     漏寫只是少學一條，下次還有機會
   - 只有真的推斷出東西才建檔。沒有就跳過，不要產生空表
   - **寫完立刻跑 `learn.py`，把規則寫進術語表。** 不要等使用者同意，也不要自己手改 `glossary.txt`
     （手改繞過長度／誤傷檢查）。指令：

     ```
     "$python" "$repo_dir/scripts/learn.py" "<那個 .ai-review.md>"
     ```

     把 stdout 裡新增了幾條規則貼給使用者即可。太短或會誤傷的，`learn.py` 會寫成註解、不啟用。
     **不要 git commit／push**，除非使用者要分享給同事。

6. **人工校對的 `.review.md`。** 使用者把填好的檔丟進來、或說「已校對／review 填好了」：
   **先跑 `learn.py` 再做別的。** 沒填「應該是」的列會被跳過，空檔不會污染詞表。
   機器剛產出、人還沒填的 `.review.md` **不要**拿去學。

## 8. 條件執行：Notion

只有工具清單裡真的有 Notion MCP 時才做。沒有就印：
「Notion MCP 未連接，會議記錄在 `<路徑>`。」

有的話依冪等規則寫入（SPEC §7.5）：

1. 以頁面標題（或錄音／逐字稿 stem）在 `notion.database_id` 查是否已有頁面
2. 已存在 → **問使用者**：更新內容／跳過／仍新建（標題加後綴）
3. 不存在 → 建立
4. 沒有搜尋能力時，改為「詢問是否寫入 Notion」，**絕不自動重複建立**

參加者與會議類型寫在開頭資訊表，不要當 database properties
（那些欄位目前不存在，SPEC §7.4）。

**只能碰「會議記錄」資料庫。** 不要寫入、修改或讀取任何專案進度資料庫。

## 9. 這個工具不做的事（使用者要求也要說明並拒絕）

- 不管理任務狀態、不改專案進度資料庫（待辦只是紀錄，狀態由專案管理系統管）
- 不同步 Figma 或設計檔資料夾
- 不做會議中即時轉錄
- 不上傳錄音／螢幕錄影到任何雲端服務。**影音檔完全不離開本機**；送給 AI 的只有逐字稿文字，以及（若有）本機抽出的畫面 JPEG
- 不做「認聲音認人」。講者 A／B 只是把不同的聲音分開，工具**不知道也不記得**誰是誰；
  跨場錄音也不會沿用同一個代號（這場的 A 跟上一場的 A 沒有關係）。
  使用者要「以後自動認出這是 Joyie 的聲音」＝要建聲紋檔案（等於留存生物特徵），
  這個工具刻意不做，說明理由並改建議：在逐字稿那張「誰是誰」表格填一次名字
