# 簡報產生器

產出**可編輯的 .pptx**，真正繼承樣板的 master、版面、字體與品牌色——不是做一個外觀相似的檔案。交付物是使用者能在 PowerPoint 開啟並繼續編輯的檔案。

**交付物是敘事，不是頁數。** 一份看起來正確但論述失敗的簡報就是失敗。力氣要花在故事順序，以及每一頁的「所以呢」。

---

## 步驟 1 — 問三個問題（不可跳過）

**在單一次 `AskUserQuestion` 呼叫中**問完（每次最多 4 題）。絕不擅自假設答案——對象決定論述方式，風格決定檔案本身。

### Q1 · 對象——對外還是對內？

| | 對外 | 對內 |
|---|---|---|
| 誰 | 客戶、政府／標案評審、合作夥伴、潛在客戶 | 自己團隊、管理層、跨部門 |
| 開場 | 他們的問題與成果；可信度很重要 | 要做的決定；跳過鋪陳信任 |
| 語氣 | 正式，不用未解釋的內部術語 | 直接，術語沒問題，問題講白 |
| 呈現 | 已驗證的成果、案例、法規符合 | 真實數字（包含難聽的）、未解風險、卡點 |
| 絕不 | 未解決的內部爭議、原始缺陷數、員工姓名 | 銷售話術、灌水、重述已知脈絡 |
| 長度 | 較長的鋪陳——先脈絡再請求 | 請求放前面；他們已有脈絡 |

若回答「兩者都要」，照**較嚴格**的（對外）做，並在對話中標出內部版該刪哪幾頁。除非明確要求，不要做成兩份檔案。

### Q2 · 風格——用哪一套視覺系統？

只提供這三個選項：

1. **公司樣板**（對象為外部時建議這個）——真正的 master 繼承。樣板路徑取自 `config.json` 或 `DECK_BUILDER_TEMPLATE` 環境變數（見下方「設定」）。其已驗證的版面與色票見 `references/company-template.md`。
2. **系統推薦**——以公司主色 `#0d63ba` 為基礎，但版面更簡潔密實。當公司樣板的公共安全框架與主題不符，或是內部快速簡報時使用。見 `references/recommended-style.md`。
3. **使用者提供的樣板**——問對方 `.pptx`／`.potx` 的路徑，先對它跑 `scripts/inspect_template.py`，把版面、色票與字體報告給對方看，再開始做。使用 `style: "custom"`，`template` 設為他們的路徑。

若對方選了公司樣板但主題與公共安全無關，用一句話說明並建議選項 2——之後仍照他們的選擇進行。

### Q3 · 語言

每次都要問。公司樣板本身的 13 頁**全是英文**，所以用它做中文簡報會混排——內部使用通常沒問題，但要提一下。選項：繁體中文／English／中英混排（英文標題、中文內文）。

**同一次呼叫中若尚未得知，也一併確認：**主題／素材來源、時長（決定頁數——每張內容頁約 **1.5–2 分鐘**），以及希望聽眾做出的那一個決定或行動。

## 設定

公司樣板的路徑因機器而異，所以不寫在這個 repo 裡。依序解析：

1. `DECK_BUILDER_TEMPLATE` 環境變數
2. `<skill>/config.json`，內容為 `{"company_template": "/path/to/Template.pptx"}`

以 `config.example.json` 為範本建立 `config.json`（該檔已被 gitignore）。若兩者皆無而 spec 又沒指定 `template`，`build_deck.py` 會直接報錯並說明怎麼設定——不會猜。

spec 裡明寫的 `template` 一律優先，所以 `custom` 風格與一次性樣板不受影響。

## 步驟 2 — 蒐集內容

三種來源，可以並用：

- **使用者提供的文件**——起草前完整讀過。報告不等於簡報：稽核的 20 項發現要變成 3 頁，不是 20 頁。
- **訪談**——從零開始時問：聽眾必須決定什麼？他們現在相信的哪件事是錯的？最強的反對意見是什麼？一次不要問超過 4 題。
- **專案程式碼／設計檔**——簡報主題是產品時，去讀 repo 或 Figma。真實截圖與真實數字勝過文字描述。

絕不編造數據。若需要某個數字但手上沒有，在該頁寫 `[待補: 上季轉換率]`，交付時在對話中列出每一個待補項。

## 步驟 3 — 取得逐頁大綱的確認（硬性關卡）

**停在這裡。不要寫 JSON spec，不要跑 `build_deck.py`。** 使用者必須先看過並確認逐頁大綱——這是他們明確的長期指示，不是建議。未經確認就產出，等於讓他們讀完一份 20 頁的成品才發現故事順序錯了。

分三個動作：

1. **把大綱寫到 `<deck-name>-outline.md`**——每頁一個區塊，讓分頁位置看得見。每個區塊要有：頁碼、版面名稱、標題、2–4 條要點、講者備註、`[image: …]` 標記。
2. **把整份大綱貼在對話裡**，不是只給摘要、也不是只給檔案路徑。使用者應該不必開任何檔案就能確認或指正。附上頁數與預估時長，讓長度一眼可判斷。
3. **明確問要不要開始做，或要改什麼**——然後等。沒回應不等於同意。「看起來不錯」是同意；針對第 4 頁的提問不是。

若對方要改，修完再貼一次。重新確認的成本很低。

只有在取得明確同意後，才進入步驟 4。

大綱格式範本，以及敘事結構（SCR、問題—解法、時序）與如何選擇，見 `references/narrative.md`。

比其他規則更重要的幾條：
- **標題要講重點，不是講題目。**「Q3 行動版流失率上升 4 個百分點」勝過「Q3 數據」。如果聽眾只讀標題，也應該能得到整個論述。
- **一頁一個想法。** 兩個想法就是兩頁。
- **最多約 6 條要點，每條約 12 字。** 超過就是文件了——移到講者備註或附錄。
- **開場講他們為何該在意，結尾給具體的請求。**

## 步驟 4 — 產生（僅在步驟 3 已確認後）

```bash
python3 ~/.claude/skills/deck-builder/scripts/build_deck.py \
  --spec /path/to/deck.json \
  --out  /path/to/output.pptx
```

依已確認的大綱寫 JSON——格式見 `references/spec-format.md`，可運作的範例在 `assets/example-company.json` 與 `assets/example-recommended.json`。只有要覆蓋既有輸出時才加 `--force`。

腳本會處理那些會無聲出錯的地方：

- 移除樣板自帶的頁面時**用 `drop_rel`**——單純呼叫 `sldIdLst.remove()` 會留下孤立的 part 與重複的 zip entry。
- **每個 run 都設定英文用 Segoe UI（`a:latin`）、中文用微軟正黑體／Microsoft JhengHei（`a:ea`／`a:cs`）**——所以一行中英混排也能正確顯示。這必須在 run 層級做；段落層級的設定會無聲失效，而公司 master 的 `titleStyle` 把 `a:ea` 設成 Open Sans（純拉丁字體），單靠繼承會讓中文標題落到 fallback 字體。除非對方要求，否則不要改；要改用 `spec["fonts"]`。
- 在**13 個公司版面中僅有 TITLE placeholder 的那 8 個**上，於安全邊界內加入文字框。
- 放大裝不下內容的 placeholder（`Content with image - right` 的 BODY 是 0.48 吋的說明列），並刪除未填入的，讓檔案裡不會出現「Click to add text」。
- **在六個深底版面上把自己加入的文字翻成白色**（`Cover`、`Title`、`Headings_Custom Photo`、`Headings_Img`、`Content Heading Dark`、`Thank you`）。否則自行加入的文字框會預設 `#13182c`，直接埋進深藍底裡看不見。
- **同一種文字排版只保留一個版面。** 底圖不算——公司樣板的 13 個版面實際是 11 個，`Table` 與 `Comparison chart` 都是 `Content Heading`，只是底圖上燒的字不同。它會轉址並每次都警告。判斷是從檔案算出來的，所以任何樣板都適用。當某張底圖**就是**選它的理由時，在 spec 設 `"collapse_layouts": false`。底色**明暗**永遠不當成底圖處理：深底版面自成一個，因為它的文字必須是亮色。

需要 `python-pptx`（已安裝 1.0.2）。若沒有：`pip3 install python-pptx`。

## 步驟 5 — 驗證後交付

一定要跑驗證器——沒跑過就不要說簡報沒問題：

```bash
python3 ~/.claude/skills/deck-builder/scripts/verify_deck.py /path/to/output.pptx
```

它會報出頁數與預估時長，並檢查文字溢出、空的 placeholder、小於 12pt 的文字、WCAG 對比（對照真實背景——該頁自己的填色、版面的、或 master 的，而非假設白底）、非品牌色、**各語系字體錯誤或缺失**、過大的表格、缺少講者備註、重複的 zip entry 與孤立的 slide part。**未解決的 `[待補: …]` 標記是錯誤**——exit code 1——所以未完成的簡報不會被誤交出去。

修掉它標出的問題再重跑。關於密度或缺少備註的警告屬於判斷題；錯誤不是。

然後在對話中簡短說明：檔案路徑、頁數、預估時長、每一個 `[待補: …]`、以及任何你做的假設。不要再貼一次大綱——那已經確認過了。

不要為了「檢查」而開啟或把檔案轉成圖片——這個環境沒有 LibreOffice。驗證器就是檢查手段。

## 絕不

- **絕不在使用者確認逐頁大綱之前產生 .pptx。** 這是使用者的長期指示。不因簡報很短、內容很明顯，或「先做個草稿給他們看」而破例——大綱是他們操舵論述的地方，在那裡改方向比在成品裡改便宜得多。
- **絕不覆蓋公司樣板。** 讀取它，一律 `save()` 到新路徑。要覆蓋任何既有輸出檔前先確認。
- 絕不編造數字、客戶名稱或成果——尤其是對外簡報，那會變成某個人得去兌現的承諾。
- 絕不在未說明的情況下超出已談定的頁數。
